## 1. Workstream Scope

### WS-1: Data Format Conversion (JSON → TOON)

| Category | Items |
|---|---|
| **In scope (Phase 1)** | Design TOON schema for all uniform arrays (`paymentLog`, `odBalanceLog`, `rateHistory`, `disbursements`, `prepayments`, `contributions`, `odBalanceAnnotations`). Build JSON↔TOON converter script (TypeScript). Round-trip fidelity tests. Byte/token benchmarks on real data. Document safe-edit protocol for LLMs. |

| **Non-goals** | Custom TOON parser in Python (use the converter to produce JSON for the engine; TOON is for LLM context only). |

All scenarios: base, prepayment, rate change, OD change, disbursement during EMI, moratorium boundary, edge cases. |

| **Non-goals** | Supporting non-reducing-balance methods. Leap-year day-count conventions (365 only). |

## 3. Success Criteria

### 3.1 Numeric Parity

- **Money values** (EMI, interest, principal, balances): Must match the TypeScript engine to the **nearest integer rupee** (±0 tolerance on `Math.round()` outputs)
- **Date values**: Must be identical strings (YYYY-MM-DD)
- **Tenure values**: Must match exactly (integer months)
- **Percentage values**: Must match to 2 decimal places

### 3.2 Token Budgets

| Report | Target | Hard Limit |
|---|---|---|
| Summary | ≤ 400 tokens | 600 tokens |
| OD Savings | ≤ 600 tokens | 900 tokens |
| Schedule (windowed) | ≤ 800 tokens | 1200 tokens |
| Simulator comparison | ≤ 600 tokens | 900 tokens |
| Ledger | ≤ 500 tokens | 800 tokens |

### 3.3 Mutation Safety

- Every mutation must show a **dry-run preview** before committing
- Every mutation must produce an **impact summary** showing what changed
- Over-allocation warnings must be surfaced (same thresholds as the app)
- No data loss: all mutations append to edit history where applicable
- Round-trip integrity: data can be converted JSON→TOON→JSON without loss

### 3.4 Functional Completeness

- A user can get the same decision-relevant information from the conversational version that they get from the app
- All 16 explicit+implicit mutations are supported as skill operations
- The simulator scenario capability is preserved (prepayment, rate, OD, disbursement)

## 4. Assumptions, Constraints, and Risks

| # | Category | Item | Mitigation |
|---|---|---|---|
| R1 | **Risk** | Claude Desktop may not support code execution (Tier C) | Phase 1 pre-generates all reports + fixtures; logic spec enables reasoning fallback |
| R2 | **Risk** | Python floating-point may diverge from JavaScript's on edge cases | Parity harness catches this; explicit rounding rules at every Math.round() boundary |
| R3 | **Risk** | TOON format has no established standard — LLMs may misparse it | Use simple tab-separated format; include explicit header and `[N]` row count; test with Claude before finalizing |
| R4 | **Risk** | Auto-deduction logic creates entries with `Math.random()` IDs — non-deterministic | Engine uses deterministic ID generation (hash of date+type) |
| R5 | **Constraint** | Google Drive has no overwrite/delete — only create/search/read | Use append-only versioned files; latest version has highest sequence number |
| R6 | **Constraint** | Data files are gitignored and contain PII (account number, personal names) | Skill and Project instructions never embed raw PII; TOON files redact account numbers |
| R7 | **Constraint** | No concurrency control in the app | Conversational version is single-user; add sequence-number check to detect stale writes |
| R8 | **Assumption** | Day count is always 365 (no leap year handling) | Document as a known limitation; revisit if user requests it. Default chosen. |
| R9 | **Assumption** | All payments are on the due date day (10th) | The engine assumes this; `paidDate` is logged but not used in calculations. Default chosen. |
| R10 | **Risk** | Phase 2 model capabilities may differ from Phase 1 | Tier system (A/B/C) ensures graceful degradation; critical path doesn't require code execution |
